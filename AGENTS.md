## Серверная логика и валидация

- Запросы к БД и транзакции размещать в `src/lib/server/db/actions`. Серверные сценарии должны взаимодействовать с БД через функции этого слоя.
- Границы транзакций определять исходя из атомарности выполняемых операций.
- Проверку входных данных выполнять на сервере независимо от наличия клиентской валидации.
- Схемы, используемые как на сервере, так и в интерфейсе, размещать вне `server`.
- Для валидации Zod предпочитать встроенные методы. `refine` и `superRefine` использовать для проверок, которые невозможно или нецелесообразно выразить стандартными средствами.
- Преобразования входных данных внутри схем допускать, если они относятся к парсингу или нормализации. Бизнес-логику и формирование прикладных сущностей выносить за пределы схем.
- При выводе ошибок формы показывать первую ошибку каждого поля, если требования конкретной формы не предусматривают иного.
- Не дублировать правила валидации в нескольких местах без необходимости.

## Технологический стек

- SvelteKit 3 и Svelte 5 — приложение и серверная логика.
- TypeScript — основной язык проекта.
- PostgreSQL — база данных; Drizzle ORM и Drizzle Kit — работа со схемой и миграциями.
- `@sveltejs/adapter-node` — сборка для запуска на Node.js.
- Стили компонентов Svelte и SCSS; для компиляции SCSS используется `sass-embedded`.
- Bits UI — доступные примитивы для сложных компонентов. Использовать через собственные компоненты проекта; простые компоненты реализовывать самостоятельно.
- `@lucide/svelte` — иконки интерфейса.
- Zod — валидация данных на границах приложения.
- `svelte-dnd-action` — перетаскивание элементов очереди. Для действий с очередью предусматривать управление без перетаскивания.
- Собственная серверная авторизация: `@node-rs/argon2` — хеширование паролей; `@oslojs/crypto` и `@oslojs/encoding` — криптографические операции и кодирование токенов. Функции авторизации пока не подключены к приложению.
- Resend — отправка писем; React Email и React — создание и рендеринг шаблонов писем. Отправка писем пока не подключена к приложению.
- Vitest — модульные и компонентные тесты; компонентные тесты запускаются в браузере через Playwright.
- ESLint и Prettier — проверка и форматирование кода.

Для серверной логики использовать загрузчики, form actions и `+server`-обработчики SvelteKit. Экспериментальные Remote Functions пока не использовать.

## Стиль кода

- Для форматирования, кавычек, точек с запятой, порядка импортов и других автоматизируемых соглашений использовать существующие настройки ESLint и Prettier. Не дублировать их правила в этом разделе.
- Самостоятельные именованные функции предпочтительно объявлять через `function`. Стрелочные функции оставлять для callback-ов и случаев, где они нужны для сохранения поведения.
- Не менять способ объявления функции, если это может затронуть `this`, `arguments`, `new.target`, типизацию, порядок инициализации или поведение.
- Если функция использует отдельные свойства объектного параметра, предпочитать деструктуризацию в параметрах. Не применять это правило, когда объект нужен целиком или преобразование может изменить типизацию либо поведение.
- Если из результата вызова используются только отдельные свойства объекта или элементы массива, предпочитать деструктуризацию при получении результата. Не применять её, если результат также используется целиком, может быть `null` или `undefined`, от него зависит сужение типов или преобразование меняет поведение.
- При изменениях стиля сохранять поведение, типы и публичные интерфейсы. Не объединять стилистические правки с изменениями функциональности, архитектуры или зависимостей.
- Не выполнять преобразования, безопасность которых не удалось установить. Оставлять такие места без изменений и кратко объяснять причину.
- Для проверки использовать существующие команды ESLint, Prettier и TypeScript в пределах изменённой области. Не запускать автоматическое форматирование всего проекта и не менять конфигурацию инструментов в рамках стилистических правок.

## Размещение компонентов и стилей

- Компоненты размещать по назначению в `atoms`, `molecules` или `organisms`. Каждый компонент хранить в отдельной папке с файлом `index.svelte`.

- Соблюдать принятую компонентную структуру и переиспользовать существующие атомарные компоненты.
