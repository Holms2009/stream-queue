# Правила разработки

## 1. Изменение правил

- Не редактировать `AGENTS.md` без согласования с пользователем, если задача напрямую не предусматривает его изменение.
- При противоречии правил и требований задачи сообщать об этом пользователю до выполнения соответствующих действий.

## 2. Порядок работы

- При получении задачи из Linear разбивать её на логически завершённые шаги и согласовывать общий список перед началом работы.
- Каждый шаг выполнять в следующем порядке:
  1. Изучить минимальный необходимый контекст.
  2. Подготовить технический план с указанием предполагаемых изменений.
  3. Представить план пользователю и дождаться согласования.
  4. Реализовать только согласованный шаг.
  5. Проверить результат и сообщить о завершении.
  6. Перейти к планированию следующего шага.
- Не приступать к реализации шага без отдельного согласования его плана. Согласование общей декомпозиции задачи не является разрешением на реализацию всех шагов.
- Не дробить задачи на избыточное количество микрошагов. Каждый шаг должен представлять собой логически завершённую часть работы.
- При обнаружении обстоятельств, требующих существенного изменения согласованного подхода, сообщать о них и согласовывать дальнейшие действия.
- Не выходить за рамки согласованного шага и не выполнять попутные улучшения без разрешения.
- Не создавать дополнительные задачи в Linear и не изменять требования существующих без согласования.
- Использовать ранее согласованные решения и собранный контекст. Не повторять их анализ без необходимости.
- Планы и отчёты формулировать кратко и предметно. Не пересказывать изученный код, общеизвестные особенности технологий и ранее согласованные решения.
- По завершении шага сообщать о результате, затронутых файлах, проведённых проверках и известных ограничениях.

## 3. Работа с кодовой базой и расход контекста

- Перед исследованием кодовой базы определять конкретные вопросы, на которые необходимо получить ответы для реализации текущего шага.
- Начинать с известных файлов, путей и определений. Если расположение нужного кода известно, не выполнять предварительный поиск по проекту.
- Если расположение неизвестно, сначала искать имена файлов, символы или точные вхождения.
- Расширять область исследования постепенно, только при наличии конкретной необходимости.
- При поиске ограничивать директории, количество результатов и окружающий контекст.
- Предпочитать чтение отдельных определений и фрагментов полному содержимому больших файлов.
- Если результат поиска обрезан или содержит слишком много совпадений, уточнять запрос вместо повторения широкого поиска.
- Не выполнять массовое чтение файлов, рекурсивное исследование всего проекта или построение полной карты кодовой базы без прямого запроса.
- Исключать из поиска зависимости, результаты сборки, кеши, сгенерированные файлы и другие нерелевантные директории.
- Не повторять чтение неизменённых файлов без конкретной причины. Учитывать уже полученный контекст.
- После согласования плана не исследовать повторно изученный код, если не появились новые обстоятельства или изменения, влияющие на реализацию.
- Не изучать внутреннюю реализацию сторонних библиотек без необходимости. Использовать существующий код проекта и доступную документацию как первичные источники.
- Не обращаться к внешним источникам, если необходимые сведения уже доступны и не требуют актуализации.
- При необходимости существенно расширить область исследования объяснить причину и согласовать это с пользователем.
- Избегать повторных поисков, проверок и инструментальных вызовов, не предоставляющих новой информации.
- Экономить контекст без ущерба корректности решения. Не сокращать необходимые проверки исключительно ради уменьшения расхода токенов.

## 4. Изменение файлов

- Изменять только файлы, непосредственно относящиеся к согласованному шагу.
- Предпочитать минимальные локальные изменения, достаточные для выполнения задачи.
- Не выполнять попутный рефакторинг, переименование, форматирование или оптимизацию несвязанного кода.
- Не переписывать существующие файлы целиком, если достаточно точечного изменения.
- Не менять публичные интерфейсы, контракты данных и существующее поведение модулей без необходимости и согласования.
- Не добавлять зависимости, новые уровни абстракции, универсальные обёртки и вспомогательные модули без обоснованной необходимости.
- Перед созданием новой реализации проверять наличие подходящих решений в непосредственно связанных модулях.
- Соблюдать существующие соглашения по именованию, структуре и организации кода.
- После реализации проверять изменения на предмет случайно затронутого кода и побочных эффектов.
- Перед завершением шага сверять фактический результат с каждым пунктом согласованного плана.
- Проверять по изменённому коду утверждения о переиспользовании логики, отсутствии дублирования, сохранении контрактов и обработке граничных случаев.
- Не заявлять о выполнении требований, которые не реализованы или не были проверены.
- При частичном выполнении требования явно указывать, что реализовано, что осталось невыполненным и почему.

## 5. Git

- При начале работы над задачей переключаться на `master`, обновлять его из удалённого репозитория и создавать от него ветку с именем, совпадающим с номером задачи, например `STR-7`.
- По завершении задачи включать в коммит **все изменения, сделанные в её ветке, независимо от автора**. Создавать коммит с кратким описанием выполненных работ, отправлять ветку в удалённый репозиторий и создавать pull request в `master`.
- Новые файлы, созданные в рамках задачи, добавлять в индекс Git автоматически и точечно, указывая каждый файл отдельно.
- Существующие файлы добавлять в индекс только по отдельной просьбе или при подготовке итогового коммита завершённой задачи.
- Повторное добавление ранее созданного агентом файла допускается, если он изменён в рамках текущей задачи.
- Не выполнять Git-операции, кроме предусмотренных этим разделом, без явного разрешения.
- Не использовать Git для исследования проекта или проверки изменений, кроме проверок, необходимых для предусмотренных операций.
- Если задача завершена без изменений файлов репозитория, не создавать пустой коммит или pull request.
- Если созданная для задачи ветка не содержит изменений, требующих сохранения, допускается удалить её после завершения задачи без дополнительного согласования.
- Перед удалением ветки убедиться, что в ней отсутствуют несохранённые изменения и уникальные коммиты, которые необходимо сохранить. Не использовать принудительное удаление при наличии неопределённости.
- Если разрешённая Git-операция завершилась ошибкой, остановиться и сообщить об этом. Не предпринимать обходные действия самостоятельно.
- В итоговом отчёте указывать результат Git-операций и созданный pull request, если он есть.

## 6. Архитектура и организация кода

- Соблюдать существующую архитектуру проекта. Не менять структуру модулей и контракты между ними по собственной инициативе.
- Разделять ответственность между компонентами интерфейса, бизнес-логикой и доступом к данным.
- Соблюдать принцип единственной ответственности: функция или модуль должны решать одну логически завершённую задачу.
- Разделять отдельные операции и их оркестрацию. Последовательности взаимосвязанных действий организовывать на уровне сценариев с использованием переиспользуемых функций нижележащих слоёв.
- Не смешивать в одной функции независимые обязанности, если их разделение улучшает понятность и сопровождение кода.
- Не дробить код на множество функций и файлов без реальной пользы.
- Не вводить универсальные решения для гипотетических будущих требований.
- Предпочитать простые, прозрачные и соответствующие текущим задачам решения.
- При наличии нескольких архитектурно значимых вариантов описывать их преимущества и ограничения до реализации.
- Не принимать самостоятельно решения, существенно влияющие на архитектуру проекта или контракты между его частями.

## 7. Серверная логика и валидация

- Запросы к БД и транзакции размещать в `src/lib/server/db/actions`. Серверные сценарии должны взаимодействовать с БД через функции этого слоя.
- Границы транзакций определять исходя из атомарности выполняемых операций.
- Проверять входные данные на сервере независимо от наличия клиентской валидации.
- Схемы, используемые как на сервере, так и в интерфейсе, размещать вне `server`.
- Для валидации Zod предпочитать встроенные методы. `refine` и `superRefine` использовать для проверок, которые невозможно или нецелесообразно выразить стандартными средствами.
- Допускать преобразования внутри Zod-схем, если они относятся к парсингу или нормализации входных данных. Бизнес-логику и формирование прикладных сущностей выносить за пределы схем.
- При выводе ошибок формы показывать первую ошибку каждого поля, если требования конкретной формы не предусматривают иного.
- Не дублировать правила валидации без необходимости.

## 8. Технологический стек

- **SvelteKit 3 и Svelte 5** — приложение и серверная логика.
- **TypeScript** — основной язык проекта.
- **PostgreSQL** — база данных.
- **Drizzle ORM и Drizzle Kit** — работа со схемой БД и миграциями.
- **@sveltejs/adapter-node** — сборка для запуска на Node.js.
- **SCSS и sass-embedded** — стили и их компиляция.
- **Bits UI** — доступные примитивы сложных компонентов. Использовать через собственные компоненты проекта; простые компоненты реализовывать самостоятельно.
- **@lucide/svelte** — иконки интерфейса.
- **Zod** — валидация данных на границах приложения.
- **svelte-dnd-action** — перетаскивание элементов очереди. Для действий с очередью предусматривать управление без перетаскивания.
- **@node-rs/argon2** — хеширование паролей.
- **@oslojs/crypto и @oslojs/encoding** — криптографические операции и кодирование токенов.
- **Resend** — отправка писем.
- **React Email и React** — создание и рендеринг шаблонов писем.
- **Vitest** — модульные и компонентные тесты.
- **Playwright** — браузерное выполнение компонентных тестов.
- **ESLint и Prettier** — проверка и форматирование кода.

Для серверной логики использовать загрузчики, form actions и `+server`-обработчики SvelteKit. Экспериментальные Remote Functions пока не использовать.

## 9. Тестирование и проверки

### Планирование тестов

- Для автоматизированного тестирования использовать Vitest.
- До создания, изменения или удаления тестов предоставлять пользователю список предполагаемых тест-кейсов для согласования.
- Для каждого тест-кейса указывать проверяемое поведение, ожидаемый результат, назначение и предполагаемый файл или уровень проверки.
- Не изменять тесты без явного согласования. Если согласована только часть списка, реализовывать только её.
- Дополнительные тест-кейсы, выявленные в ходе работы, согласовывать отдельно.
- Основывать тесты на согласованных продуктовых правилах. Не закреплять тестами предположения о неопределённом поведении.
- Для многоэтапной задачи допускается сначала согласовать общие сценарии тестирования, а конкретные тест-кейсы и уровни проверки уточнять перед реализацией соответствующего шага.
- Не готовить подробные тест-кейсы для отложенных или ещё не согласованных этапов.

### Требования к тестам

- Для новой и изменённой бизнес-логики предлагать тесты основных сценариев, значимых граничных случаев, некорректных входных данных и обработки ошибок.
- При исправлении ошибки по возможности предлагать регрессионный тест, воспроизводящий исходную проблему.
- Приоритет при тестировании очереди отдавать правилам порядка заявок, активной заявке и переходам между состояниями.
- Компонентные тесты предлагать для значимых пользовательских сценариев, а не для каждой детали разметки или оформления.
- Интеграционные тесты серверной логики и БД предлагать по мере появления соответствующих сценариев и тестовой среды.
- Не писать тесты исключительно ради покрытия.
- Предпочитать проверку публичного поведения модулей, а не деталей реализации.
- Не подменять проверку поведения чрезмерным мокированием.
- Не изменять существующие ожидания тестов без обоснования и согласования.
- Прохождение существующих тестов не считать подтверждением нового поведения, если оно не покрывается их проверками.

### Выполнение проверок

- После реализации каждого шага проводить применимые проверки.
- Запускать связанные с изменениями тесты Vitest.
- Дополнительно выполнять необходимые проверки типизации, ESLint и синтаксиса существующими командами проекта.
- Полную сборку и весь набор тестов запускать, когда локальных проверок недостаточно или изменения затрагивают общую инфраструктуру приложения.
- Не повторять одинаковые проверки без изменений, способных повлиять на их результат.
- Не изменять конфигурацию инструментов ради успешного прохождения проверок.
- Если проверка завершилась ошибкой, определить её причину. Исправлять проблемы, относящиеся к текущему шагу; о посторонних сообщать отдельно.
- Если обязательную проверку выполнить невозможно, прямо сообщать об этом.
- В отчёте указывать фактически проведённые проверки, их результаты и границы покрытия. Не представлять частичную проверку как подтверждение всей функциональности.

## 10. Стиль кода

- Для форматирования, кавычек, точек с запятой, порядка импортов и других автоматизируемых соглашений использовать существующие настройки ESLint и Prettier. Не дублировать их правила.
- Самостоятельные именованные функции предпочтительно объявлять через `function`. Стрелочные функции использовать для callback-ов и случаев, где они необходимы или оправданы.
- Не изменять способ объявления функции, если это может затронуть `this`, `arguments`, `new.target`, типизацию, порядок инициализации или поведение.
- Если используются отдельные свойства объектного параметра, предпочитать деструктуризацию в параметрах функции.
- Если из результата вызова используются только отдельные свойства объекта или элементы массива, предпочитать деструктуризацию при получении результата.
- Не применять деструктуризацию, если объект необходим целиком, возможны `null` или `undefined`, требуется сохранение сужения типов либо преобразование может изменить поведение.
- Не выполнять стилистические преобразования, безопасность которых не установлена.
- Не совмещать несвязанные стилистические изменения с функциональными или архитектурными.
- Для проверки использовать существующие инструменты в пределах затронутой области. Не форматировать весь проект и не изменять настройки инструментов без согласования.

## 11. Компоненты и стили

- Размещать компоненты по назначению в `atoms`, `molecules` или `organisms`.
- Каждый компонент хранить в отдельной папке с файлом `index.svelte`.
- Стили компонента хранить рядом с ним в отдельном SCSS-файле и подключать через `@use` в `<style lang="scss">`.
- Стили, относящиеся только к странице, хранить рядом с соответствующей страницей.
- Публичные экспорты компонентов собирать в `index.ts` соответствующей категории и импортировать через настроенный алиас.
- Переиспользовать существующие компоненты. Не создавать новые ради формального разделения небольших фрагментов разметки.
- Для селекторов, которым необходимо действовать за пределами scoped-стилей компонента, использовать блок `:global { ... }`. Остальные стили оставлять локальными.
- Именовать классы элементов с префиксом компонента, например `request-add-form__title-input`.
- Предпочитать Flexbox и Grid. Абсолютное позиционирование применять при обоснованной необходимости.
- Использовать `rem` для размеров и отступов в соответствии с принятой системой проекта.
- Не добавлять лишние DOM-обёртки и уровни вложенности без функциональной необходимости.
- Избегать сложных вложенных тернарных операторов. Выносить нетривиальную логику выбора в отдельные функции или понятные выражения.
- Учитывать длинные строки, переполнение, переносы текста и отсутствие данных.
- Не изменять существующую структуру или поведение интерфейса без необходимости.
- Не добавлять новые брейкпоинты без согласования.
- Не удалять существующие файлы стилей, подключения и пустые файлы-заготовки в рамках попутной уборки.

## 12. Общие ограничения

- Не выполнять действия, не связанные с поставленной задачей.
- Не устанавливать пакеты, инструменты и расширения без согласования.
- Не изменять конфигурацию проекта и окружения без необходимости и согласования.
